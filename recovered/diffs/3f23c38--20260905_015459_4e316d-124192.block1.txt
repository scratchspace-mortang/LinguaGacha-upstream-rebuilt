## Why the re-render loop was the actual root cause

`spelling-activity-store.ts` `applySnapshot` originally short-circuited only on `revision < current`. When the SSE handler fired for a re-emit of the same snapshot (the same revision N + same pending/active), the guard didn't trip; `snapshot = normalized_snapshot` assigned a fresh object; `for (const listener of listeners) listener()` synchronously called React's `forceStoreRerender`; React scheduled a re-render; the falling-edge `refresh_snapshot` effect fired inside the commit; that effect set multiple `useState` values; React detected nested updates and threw "Maximum update depth exceeded". The handler's `catch` block then reported the error. Repeat per SSE event → hundreds of errors per Re-spellcheck.

The fix is at the source: when the data is identical, do not reassign and do not notify. React's `useSyncExternalStore` reads `getSnapshot()` between renders; if the snapshot reference is the same, no re-render. The structural-equality guard is the minimum change that breaks the cascade.

## Decisions to revisit if needed

- **Other stores** (`task-snapshot-store.ts`, `runtime-activity-store.ts`) have the same `applySnapshot` shape without the structural-equality guard. They don't manifest the bug because their data doesn't change at high frequency. If task or runtime activity starts updating in tight bursts, apply the same guard.
- **Indicator timing**: the pending indicator is driven by `store.pending.length > 0`. If the backend emits a zero-pending snapshot before all in-flight writes have settled, the indicator might flicker. The `batch_end` event from the backend is the correct settle signal; the frontend should use that rather than `pending.length` alone.
